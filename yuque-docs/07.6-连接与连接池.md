# 7.6 连接与连接池（重点）

## 什么是连接?

在讲解连接池之前,我们先讲解什么是连接。在我们这套RPC框架中,内部维护的是**TCP 连接**。好比电话线, 客户端和服务端只有建立连接,建立好这条电话线,才能通信。

建立连接不是一瞬间就完成的,而是完成**三次握手**之后才建立来的。

每一个 TCP 连接都会占用：
- 文件描述符（FD）
- 内存缓冲区
- 内核 socket 资源

如果每个请求都新建立连接,那么如果1秒需要发送1000次请求,就需要在1s建立1000条连接。在操作系统中,一个进程中所能创建的文件描述符也是有限制的,且创建大量连接会导致 CPU 飙升、FD 被耗尽、服务崩溃。

## 什么是连接池? 为什么需要连接池?

提前创建好一些 TCP 连接，放在这个池子里，大家重复使用——这个池子就是**连接池**。

就像：
- 不要每次打电话都重新拉电话线
- 而是装好 10 条固定电话线
- 需要打电话时直接用

### 为什么 RPC 需要连接池？
- 建立 TCP 连接非常昂贵
- 三次握手耗时
- 创建太多连接会耗尽资源

所以我们通过连接池,**复用了连接**——这叫做 RPC 端的**连接复用**。

## 什么是请求复用?

一般来说,连接复用的做法就是,一个进程中的多个线程/协程在从连接池中获取连接后,这个连接就会从连接池弹出,直到这个线程/协程用完了这个连接,归还到连接池后,其他线程/协程才能继续使用相同的连接。

这样做的坏处是,做不到针对同一个连接的复用。不利于高并发场景。因为针对同一个连接,不同线程/协程是串行执行的,效率很低。

针对 HTTP/1.0,请求端和服务端都是只能串行,不支持真正的复用;而 HTTP/1.1,服务端依旧存在串行现象。

而**请求复用**,是针对同一个连接,可以被多个线程/协程都同时拥有。当然,在同一个封装的连接中,对一些必要的场景,会进行加锁操作——这就是请求复用。

### 思考：如何区分不同请求?

针对不同线程/协程都是同一个连接,服务端这边是无感知的,不清楚这个请求来自于哪个线程/协程。那么怎么辨识呢?

**答: 利用 requestID / streamID**

像 HTTP/2.0 支持真正的多路复用：同一个 TCP 连接上可以同时传输多个请求/响应,通过 stream ID 来区分。
